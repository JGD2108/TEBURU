## Context

See proposal.md for motivation. The deployed flow currently sends a PDF to an application API route and browser reports show non-JSON responses, 400 and 500 errors, a missing route, and a 413 response. A 413 generated by the hosting edge cannot be converted into an application JSON response because the request is rejected before the route executes.

## Goals / Non-Goals

**Goals:**

- Keep browser-to-server control requests small while supporting the configured PDF import limit.
- Make API and configuration failures deterministic, safe to render, and diagnosable in production.
- Preserve restaurant isolation throughout authorization, storage, import-job creation, and retry.

**Non-Goals:**

- Changing PDF extraction quality, draft review rules, or publication behavior.
- Circumventing hosting-provider limits for arbitrary public uploads.
- Exposing configuration secrets or storage credentials to the browser.

## Decisions

### Use an authorized direct-to-private-storage upload handshake

The browser requests a short-lived, restaurant-scoped upload authorization from a small control endpoint, uploads the PDF directly to the private source-document storage destination, then submits an object reference to finalize the import. Finalization verifies authorization ownership, object existence, media type, size, and configured limits before creating a job.

This avoids Vercel's application request-body limit and retains server-side authorization. Increasing route limits or proxying multipart uploads was rejected because platform-level 413 responses occur before application code.

### Standardize application errors and defensively consume intermediary responses

All application API routes use one JSON error envelope with a stable code and safe message. The browser checks HTTP status and content type before parsing; a non-JSON response is represented as a generic transport failure, preserving the status and request identifier when available for support diagnostics.

Assuming every non-success response is JSON was rejected because 404 pages, hosting limits, and reverse-proxy failures can return text or HTML.

### Make public settings a readiness contract

The public-settings endpoint returns a JSON document for reachable application states, including a non-secret import availability/readiness indicator. The UI disables submission and explains the availability state before it creates a job. Detailed configuration failures are server-logged with correlation identifiers but not returned to unauthenticated callers.

Returning a bare 400 for missing configuration was rejected because it gives the UI no safe contract and causes the observed failure cascade.

### Instrument the upload-to-job handoff

Correlate authorization, upload finalization, job creation, and analysis-start failures with one request/import identifier. Capture failure code, status, and safe context in server logs; do not log document contents, signed URLs, secrets, or personal data.

## Risks / Trade-offs

- [A direct upload succeeds but finalization is interrupted] → Store an expiring pending-upload record and make finalization idempotent; clean unfinalized objects through lifecycle rules.
- [A signed upload authorization leaks] → Keep it short-lived, single-object, restaurant-scoped, and limited to PDF MIME type and the configured maximum size where supported.
- [A hosting intermediary returns a non-JSON error] → Detect content type in the client and present a generic retry/support state instead of parsing the payload.
- [Configuration drift reintroduces server errors] → Validate startup/runtime configuration, publish readiness, and verify the production deployment flow.

## Migration Plan

1. Add the error envelope, client response guard, readiness contract, and request correlation while retaining the current import path for supported small documents.
2. Add direct private-storage upload authorization and finalization, then switch the admin UI to the new flow behind a rollout flag.
3. Verify successful small and large PDF imports plus all documented error paths in the deployment environment.
4. Remove the multipart import path after the direct flow is stable; rollback by re-enabling the small-document path while preserving JSON error handling and readiness reporting.
